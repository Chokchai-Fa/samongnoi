# Manage secrets & env vars

Every value has exactly **one source of truth**, decided by who creates it (see "Secrets &
config" in `CLAUDE.md`). First classify the value, then follow that kind's checklist. Every
touchpoint in a checklist must be updated in the **same PR** — a half-wired secret either fails
`env.ts` validation at runtime or leaks into the wrong place.

## Step 1 — classify

| Question | Kind |
|----------|------|
| Only Terraform / wrangler need it to talk to a provider? | **1. Provider credential** |
| Terraform creates it (DB URL, Redis token, random password)? | **2. Generated secret** |
| A human gets it from a third-party dashboard (email API key, OAuth secret)? | **3. Third-party secret** |
| API needs it, but it's not secret (feature flag, CORS origin)? | **4a. Worker var** |
| The browser needs it (API URL, public analytics key)? | **4b. Frontend var** (public!) |

If the browser needs something secret — stop. It can't be secret in a SPA; route the call through
the API instead and tell the user.

## Setting GitHub secret values — `scripts/setup-github-secrets.sh`

GitHub Actions secrets (kinds 1 and 3) are set with the repo's script, which reads values with
hidden input (or from a gitignored `.secrets.env`) and pipes them to `gh secret set` via stdin.
**Claude never handles the values.**

- **Never ask the user to paste a secret into the chat**, and if they offer, decline and point
  them to the script — chat content persists in the conversation history.
- Tell the user to run it themselves with the `!` prefix so it runs in this session but the
  hidden prompt stays on their terminal:
  ```
  ! scripts/setup-github-secrets.sh --repo <owner>/<repo>
  ```
  Enter on an empty prompt skips a secret (keeps its current value), so re-running to set just
  one new secret is fine.
- File mode (e.g. bulk setup): user fills `.secrets.env` with `NAME=value` lines →
  `scripts/setup-github-secrets.sh --repo <owner>/<repo> --from-file .secrets.env` → deletes the
  file. The script refuses files that aren't gitignored and only uploads names it knows.
- **Claude may run `--check` itself** — it prints only names with ✓/✗, never values:
  `scripts/setup-github-secrets.sh --repo <owner>/<repo> --check` (exit code 1 if any missing).
- Claude may also run `gh secret list --repo <owner>/<repo>` (names + dates only).
  Claude must not run `gh secret set` with a value, or `gh secret delete`, without the user's
  explicit go-ahead for that specific secret.
- The script's `SECRETS` array is the **list of required GitHub secrets** — keep it in sync with
  `CLAUDE.md`, `infra/README.md` §1.8, and the workflows when adding or removing one.

Naming: `UPPER_SNAKE_CASE` env vars. GitHub forbids secret names starting with `GITHUB_`. Terraform outputs use the same name in `lower_snake_case`
(`database_url` → `DATABASE_URL`) — `.github/actions/terraform-outputs` relies on that mapping.

## Step 2 — ADD

### Kind 1 — provider credential
1. Add `"NAME|where to get it (README §)"` to the `SECRETS` array in
   `scripts/setup-github-secrets.sh`.
2. Ask the user to create the token with the **minimum scope** at the provider, then set it with
   `! scripts/setup-github-secrets.sh --repo <owner>/<repo>` (skip the others with Enter).
   Verify with `--check`.
3. Pass it via `env:` on every Terraform job that needs it: `ci.yml` (terraform-plan),
   `deploy.yml` (infra), `drift.yml`. Use the provider's native env var name when it has one.
4. Add it to the GitHub secrets list in `CLAUDE.md` (CI/CD section), to the provider setup
   steps and the §1.8 table in `infra/README.md`.
5. Local: document it in `.envrc.example` (direnv); the real `.envrc` stays gitignored.

### Kind 2 — generated by Terraform
1. `infra/`: create/expose the value, e.g. a `random_password` resource or an attribute of a
   Neon/Upstash resource, and add an output in `infra/envs/prod/outputs.tf`:
   ```hcl
   output "better_auth_secret" {
     value     = random_password.better_auth_secret.result
     sensitive = true
   }
   ```
   Module outputs carrying it must also be `sensitive = true`.
2. `.github/workflows/deploy.yml` → `app` job → Deploy Worker step: add the name to `secrets:`.
   (The `terraform-outputs` action already exports and masks it — no other CI change.)
   If migrations or the web build need it too, it's already in the job env.
3. API code: steps under "Every Worker secret / var" below.

### Kind 3 — third-party secret
1. Add `"NAME|where to get it (README §)"` to the `SECRETS` array in
   `scripts/setup-github-secrets.sh`, then ask the user to set it with
   `! scripts/setup-github-secrets.sh --repo <owner>/<repo>`. Verify with `--check`.
2. `deploy.yml` → `app` job → Deploy Worker step:
   ```yaml
   env:
     RESEND_API_KEY: ${{ secrets.RESEND_API_KEY }}
   with:
     secrets: |
       ...
       RESEND_API_KEY
   ```
3. Add it to the GitHub secrets list in `CLAUDE.md` and the §1.8 table in `infra/README.md`.
4. API code: steps under "Every Worker secret / var" below.

### Kind 4a — non-secret Worker var
1. `apps/api/wrangler.toml` → `[vars]`: add `NAME = "value"`.
2. API code: steps under "Every Worker secret / var" below (skip `.dev.vars.example` — `[vars]`
   already applies to `wrangler dev`; override locally in `.dev.vars` only if needed).

### Every Worker secret / var (kinds 2, 3, 4a)
1. `apps/api/src/env.ts`: add the field to the zod schema with the tightest type
   (`z.string().url()`, `z.string().min(32)`, `z.enum([...])`).
2. Regenerate binding types: `pnpm --filter api wrangler types` and commit
   `worker-configuration.d.ts`.
3. Secrets only: add a placeholder to `apps/api/.dev.vars.example` with a local-dev value or
   comment on where to get one (e.g. docker compose URL). Add it to your local `.dev.vars` too.
4. Access it only through the validated env / `deps` (e.g. in `middleware/deps.ts`), never by
   reading `c.env.X` inside services.
5. Tests: add it to any test env fixture so `env.ts` validation passes.

### Kind 4b — frontend var (public)
1. Name must start with `VITE_`. Confirm with the user it is OK to be **public**.
2. `apps/web/src/lib/env.ts`: add to the zod schema.
3. `apps/web/src/vite-env.d.ts`: add to `ImportMetaEnv`.
4. `turbo.json` → `build` task `env`: add the name (strict env mode drops undeclared vars).
5. Source of the value in CI: `deploy.yml` → `app` job → "Build web + api" step `env:`
   (a static value, or a non-sensitive Terraform output exported by `terraform-outputs`).
   The API URL is never needed — the SPA calls the same-origin `/api`.
6. `apps/web/.env.example`: add with a local value.

## Step 3 — REMOVE

Order matters: stop **using** it before you stop **providing** it.

1. Remove all reads from code (`grep -rn NAME apps packages`) and from `env.ts` schemas.
2. Remove the touchpoints added above, for its kind:
   - `deploy.yml` `secrets:` list / step `env:` / Build step
   - `infra/envs/prod/outputs.tf` output (and the resource, if nothing else uses it)
   - `wrangler.toml` `[vars]`, `turbo.json` `env`, `vite-env.d.ts`
   - `.dev.vars.example`, `.env.example`, `.envrc.example`
   - `CLAUDE.md` / `infra/README.md` lists
   - the `SECRETS` array in `scripts/setup-github-secrets.sh` (kinds 1, 3)
3. Regenerate types: `pnpm --filter api wrangler types`.
4. **Worker secrets are not deleted by deploys** — they persist on the Worker. After the PR is
   deployed, delete the stale one (ask the user before running it):
   `pnpm --filter api exec wrangler secret delete NAME`
5. Kinds 1, 3 — after the PR is merged and deployed, delete the GitHub secret (ask the user
   first; Claude may run it once they agree, it needs no value):
   `gh secret delete NAME --repo <owner>/<repo>`. Then tell the user to **revoke the
   credential at the provider** — deleting it from GitHub doesn't invalidate it.

## Rename
Treat as **add new → deploy → remove old**, in two PRs, so the running Worker is never missing
a value.

## Rotate
- Kind 2: PR that runs `terraform apply -replace=<resource address>` via the normal pipeline
  (e.g. note in the PR, or temporarily bump a `keepers` value on `random_password`). The next
  `deploy.yml` run pushes the new value.
- Kinds 1 / 3: user creates the new value at the provider → sets it with
  `! scripts/setup-github-secrets.sh --repo <owner>/<repo>` (Enter to skip the others) →
  re-run `deploy.yml` (`gh workflow run deploy.yml --repo <owner>/<repo>`, with the user's
  go-ahead) → user revokes the old value.

## Never
- Never write a real secret value into any file, commit, PR description, log line, or chat reply.
- Never ask for, accept, or repeat a secret value in chat; never pass one as a command-line
  argument (`gh secret set X --body …` lands in shell history and process lists) — use the script.
- Never put secrets in `wrangler.toml`, `VITE_*`, `turbo.json`, or Terraform `.tfvars` committed
  to git.
- Never `echo` a secret in a workflow step; never set `sensitive = false` to "make it work".
- Never run `wrangler secret put/delete` or `terraform apply` against production without the
  user's explicit go-ahead.

## Done checklist
- [ ] Kind identified and the matching checklist fully applied
- [ ] `pnpm typecheck` and `pnpm test` pass (env schemas + generated types in sync)
- [ ] `terraform fmt -check` / `terraform validate` pass if `infra/` changed
- [ ] Example env files and `CLAUDE.md` lists updated
- [ ] `SECRETS` array in `scripts/setup-github-secrets.sh` matches the workflows (kinds 1, 3)
- [ ] `setup-github-secrets.sh --check` passes (once the user has set the value)
- [ ] User told about any manual step: value to set via the script, GitHub secret to delete,
      credential to revoke, stale Worker secret to delete after deploy
